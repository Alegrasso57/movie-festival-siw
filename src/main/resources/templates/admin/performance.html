Discussione delle scelte

La differenza importante tra le tre strategie è il numero di query SQL eseguite, più significativo del tempo assoluto misurato qui su pochi record.

LAZY è il fetch type di default delle associazioni JPA: carica prima gli oggetti principali con una query, poi esegue una query aggiuntiva per ogni associazione effettivamente usata (il regista di ogni film, o la collezione di film di ogni festival). È il classico "problema N+1": con 5 film servono 6 query (1+5), con 4 festival ne servono 5 (1+4).

JOIN FETCH è una JPQL esplicita scritta nel repository (es. JOIN FETCH f.regista) che recupera tutto in un'unica query con un JOIN, eliminando le query N+1. Quando l'associazione è una collezione (qui, i film di un festival, relazione @ManyToMany), il JOIN produce una riga duplicata del festival per ogni film collegato: per questo il metodo usa DISTINCT, altrimenti verrebbero restituite più copie dello stesso festival.

@EntityGraph ottiene lo stesso risultato (1 query, associazione già popolata) in modo dichiarativo: si annota il metodo del repository indicando quali associazioni includere, invece di scrivere la JPQL a mano. È più leggibile e riusabile, ma nei test qui sopra risulta leggermente più lento della JOIN FETCH esplicita: è normale, perché Hibernate deve prima tradurre l'EntityGraph nella query effettiva, un piccolo overhead che la JOIN FETCH (già scritta come JPQL statica) non ha.

Per questo motivo LAZY resta la scelta corretta come comportamento di default delle associazioni (evita di caricare sempre tutto il grafo delle entità), mentre JOIN FETCH ed EntityGraph vanno usati solo nei punti dell'applicazione — come le pagine elenco di Film e Festival — dove si sa già che quell'associazione servirà subito dopo.
